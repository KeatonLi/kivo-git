# Kivo Git 功能规划与 Cherry-pick 交互说明

状态：产品讨论稿（2026-09-26）
原型：[Git Operations prototype](./prototypes/git-operations.html)

## 这份文档要解决什么

Kivo Git 的承诺是让 VS Code 用户在一个连贯的工作流里完成提交、分支同步和历史审阅，同时继续使用 VS Code 原生 diff 与 merge editor。本文把现有能力、缺口和建议行为写清楚，供产品审阅后分阶段实现。

原型使用虚构提交和本地交互，不会调用 Git，也不代表这些功能已在扩展中实现。当前重点审阅 Cherry-pick 的安全边界与冲突恢复体验。

界面分区遵循 VS Code 布局：Commit 与工作区改动在左侧 Activity Bar 视图；History 在底部 Panel。History 左侧 branch 树显示本地/远程分支和标签；当前分支行以小箭头和数字提示待推送、待拉取提交数。Fetch、Pull、Push 位于 History 顶部，提交列表和选中提交详情位于 branch 树右边。

原型还提供可体验的交互：拖动调整 Commit 侧栏与底部 Panel 尺寸；在 changelist 间移动和排序文件、创建/重命名/删除 changelist；折叠本地/远程 branch 分组并从分支右键菜单操作；按搜索、ref、作者、时间和路径筛选提交；Ctrl/Shift 多选提交，或将提交拖到 branch 上发起 Cherry-pick；通过冲突、空补丁和 merge commit 场景预览恢复流程。原型中的 Git 反馈均为模拟状态。

History 的 branch 树行可显示本地分支与远端跟踪分支的 ahead/behind 数量：向上箭头表示待推送提交，向下箭头表示待拉取提交。branch 导航区只显示分支与标签；同步操作集中在 History 顶部，避免重复显示同一组数字和按钮。左侧 Commit 视图分上下两区，可拖动中间分隔线调整高度：上区显示改动列表、提交信息输入框和提交按钮；下区显示可点击的近期提交，再显示仓库状态、改动摘要与提交检查卡片。改动摘要包括文件总数、修改与新增数量、changelist 数量；拖动文件或增删 changelist 时同步更新。提交检查提示文件数量和提交信息是否填写。

## 已有能力与缺口

| 工作流 | 当前状态 | 备注 |
| --- | --- | --- |
| 查看工作区状态、选择文件、changelist、提交 | 已有 | 支持 Commit 与 Commit and Push |
| 历史、提交图、提交详情与文件 diff | 已有 | 支持搜索、ref、作者、日期、路径筛选 |
| 本地/远程分支 | 已有 | checkout、创建、合并、重命名、删除 |
| 远程同步 | 已有 | fetch、push、pull；pull 有 merge/rebase/fast-forward only 策略 |
| 标签 | 部分已有 | 可创建标签；标签后续管理能力需核对 |
| Cherry-pick | 缺失 | 没有命令入口、执行方法或序列状态恢复 |
| Revert commit | 缺失 | 历史视图没有反向提交流程 |
| Merge 冲突处理中心 | 缺失 | 冲突后继续/中止尚无完整引导流程 |
| Stash / shelf | 缺失 | 暂存工作区以便切换分支 |
| Reset、交互式 rebase、Amend、按 hunk 暂存 | 缺失 | 属于后续高级工作流 |

“已有”以当前仓库实现为准，不等于所有边界场景都通过产品验收。开发前仍需为破坏性操作补齐行为测试和失败恢复验证。

## 设计原则

1. **明确目标。** 执行前始终展示仓库、当前分支、目标分支、提交数和提交顺序。
2. **保护未提交工作。** 有未提交改动时说明风险；不会自动丢弃或覆盖。确需临时收起时，必须展示 stash 行为与恢复方式。
3. **原生编辑器处理代码冲突。** 冲突文件进入 VS Code 原生 Merge Editor；Kivo Git 负责显示进度、冲突清单、继续、跳过与中止入口。
4. **状态来自 Git。** 按 Git 的实际 sequencer / merge 状态恢复界面；窗口重载后不凭前端缓存推断成功或失败。
5. **失败可理解、可恢复。** 命令失败显示原因和可用下一步。已产生的部分结果、当前步骤和恢复操作要讲清楚。
6. **危险操作显式确认。** Reset、强制覆盖、删除分支等展示影响范围；默认选择最保守选项。

## Cherry-pick 用户流程

入口放在 History 提交行右键菜单和提交详情操作区。单选提交可以直接发起；多选提交时显示选择数量和顺序预览。

### 执行前检查

- 验证当前仓库仍是发起操作的仓库，当前分支仍可写。
- 展示目标分支；默认是当前分支，不允许用户误以为会切换分支。
- 展示完整提交列表、短 hash、提交说明及应用顺序。多个提交按照祖先到后代（旧到新）应用，用户可在执行前调整顺序。
- 检查 merge/sequencer 等未完成操作。已有 Git 操作未结束时，先引导用户继续或中止该操作，不启动嵌套流程。
- 工作区不干净时默认阻止直接执行并说明原因。未来若支持自动 stash，要明确列出 stash、应用 cherry-pick、恢复 stash 的步骤，以及恢复冲突时的处理方式。
- 提供取消和返回历史的出口，不改变仓库状态。

### 运行状态

显示“第 N / M 个提交”、当前提交、已完成数、目标分支和可用操作。进度以 Git 状态为准，不以进程启动或 UI 点击作为成功依据。

| 情况 | 建议行为 |
| --- | --- |
| 普通提交成功 | 前进到下一项；全部成功后显示结果和新工作区状态 |
| 多提交序列成功一部分 | 保留已完成的提交；清楚标记已完成、当前和剩余项 |
| Merge commit | 执行前必须选择 mainline parent；显示父提交分支/hash，解释选择哪一侧决定被移植的差异；不得静默默认 |
| 冲突 | 停在当前提交，显示冲突文件；提供 VS Code Merge Editor 入口。所有冲突解决并写入 index 后才启用 Continue |
| Skip | 跳过当前提交并进入下一项；保留此前已应用提交，执行前说明后续列表 |
| Abort | 仅取消当前未完成序列并回到操作开始前的 Git 状态；不能撤销序列开始前已有的用户更改。中止失败时保留恢复指引 |
| 空提交 / 已包含 | 默认不生成隐式空提交。说明补丁为空或已存在，提供 Skip；显式选“保留空提交”后才创建空提交 |
| 工作区文件变化 | 外部变化可能影响检查结果；执行前再次检查状态，变化时要求重新确认 |
| 扩展重载 / VS Code 重启 | 重新读取 Git sequencer 状态并恢复继续、跳过、中止选项；若无法确认状态，显示诊断而非猜测 |
| 命令取消/进程失败 | 区分“尚未开始”“部分提交已应用”“当前冲突中”；保留 Git 返回信息和恢复入口 |

### 完成结果

成功后展示提交数、目标分支、最后应用的提交及工作区变化。用户可打开 Changes 检查差异，之后自行提交。Cherry-pick 本身通常会生成新 commit；若启用仅应用变更的特殊模式，需另行设计，不纳入第一版。

## Git 操作信息架构

日常操作按用户目的组织，避免把所有命令塞入一个按钮组：

| 目的 | 操作 | 入口建议 | 风险提示 |
| --- | --- | --- | --- |
| 保存工作 | Commit、Commit & Push、选择文件/changelist | 左侧 Commit 视图 | 空提交信息、部分提交范围 |
| 同步协作 | Fetch、Pull、Push | 仓库状态与 History 顶栏 | 未推送提交、非快进、认证/网络失败 |
| 切换上下文 | Checkout、创建/重命名/删除分支 | 分支导航树和分支菜单 | 工作区改动、当前分支不可删除、远端分支跟踪 |
| 移植修复 | Cherry-pick 一个或多个提交 | History 行菜单、详情 | 工作区、merge commit、空提交、冲突、部分成功 |
| 撤销变更 | Revert commit；之后评估 Reset | History 行菜单 | Revert 创建新提交；Reset 会移动分支并可能丢改动 |
| 暂存现场 | Stash、Apply/Pop/Drop stash | Commit 面板或分支切换提示 | Pop 冲突；Drop 不可轻易恢复 |
| 标记版本 | Create / Delete / Push tag | History 与 Tags | 已推送标签的重写影响 |
| 解决冲突 | Merge Editor、Continue / Abort merge/rebase/cherry-pick | 操作状态中心与 Changes | 冲突未解决时禁用继续 |

## 发布建议

### 第一阶段：Cherry-pick 与可恢复的冲突体验

- 单提交/多提交选择，顺序预览和目标分支提示。
- clean-worktree 前置检查；merge commit mainline 选择。
- 冲突文件清单、Merge Editor 打开、解决后 Continue、Skip、Abort。
- 空提交/已应用提交处理，部分完成结果展示。
- 重载后读取 Git 实际状态并恢复序列 UI。
- 所有危险和异常分支的自动化测试及真实 Git 仓库端到端测试。

### 第二阶段：Revert、Stash 与一致的操作状态

- Revert 单个提交和冲突恢复。
- Stash 保存/查看/应用/恢复/删除；分支切换时提供安全路径。
- 把 merge、pull --rebase 与 cherry-pick 的冲突/继续/中止能力统一呈现。
- 网络、认证、非快进和 hooks 失败提供可行动的结果状态。

### 第三阶段：高级历史编辑

- Reset 的 soft/mixed/hard 区别与影响预览，hard 必须显式二次确认。
- 交互式 rebase 与提交重排、合并、编辑说明。
- Amend 与按 hunk 暂存。
- 文件历史、blame、标签管理和键盘操作完善。

阶段优先级是建议，产品审阅后可调整。历史编辑操作会改变提交图，应晚于 Cherry-pick、Revert、Stash 等日常安全流程。

## Cherry-pick 验收标准

- 从 History 选择一个提交，可以看见目标分支和提交摘要，并取消而不改变仓库。
- 多选可以核对顺序；序列部分失败时明确保留已成功部分。
- merge commit 未选择 mainline 时不能启动。
- dirty worktree 和正在进行的 Git 操作会阻止误启动，并给出明确下一步。
- 冲突时可打开原生 Merge Editor；未解决时 Continue 不可用；解决后可继续、跳过或中止。
- 空补丁不静默生成空提交；用户显式确认后才能保留。
- 扩展重载或 VS Code 重启后能从 Git 状态恢复正在进行的操作。
- 成功、部分成功、失败和中止都有清晰结果，且不会丢弃 Cherry-pick 开始前的用户更改。
- 覆盖 Windows、macOS、Linux 的 Git 行为差异、路径含空格/非 ASCII、hooks、取消和进程异常。

## 审阅问题

1. Cherry-pick 第一版是否仅允许干净工作区，还是也要把自动 stash 纳入第一版？建议先要求 clean worktree，减少恢复流程的组合复杂度。
2. 多提交选择是否允许用户拖动排序？建议第一版固定为旧到新，并在执行前清楚预览。
3. 空提交是否默认跳过？建议默认停下并让用户选 Skip 或显式保留。
4. Revert 与 Stash 是否列入 Cherry-pick 后的紧接阶段？
