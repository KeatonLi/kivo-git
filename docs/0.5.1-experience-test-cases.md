日期：2026-10-03。评估基线：main `19b4f71`，版本 0.5.1。本轮只写用例和评估，不修改产品实现。

这些验证使用生产 Webview 代码与固定数据，不能替代原设备输入法、鼠标/触控板和完整原生 Git 流程。36 个全流程用例、R06 与下文其他待测项保持原有验收范围。

目标：完成一次真实开发任务时，文件能认清、提交范围能预测、操作不中断、结果能确认。现有功能测试通过，不代表这四项目标已经通过体验验收。

## 本轮结论

最需要优先处理的是搜索输入、历史审阅和窄面板阅读的连续性；提交范围的理解也需要独立验收。先修这些，再决定 0.6 新功能。

本轮通过生产 Webview 代码与固定数据复现了以下问题；这不是完整的原生 Git 流程验收：

| 编号 | 问题 | 实际观察 | 影响 |
| --- | --- | --- | --- |
| F01 | 搜索中间改字不跟手 | `README` → Home → 输入 X，光标跳到第 7 位；再输入 Y 得到 `XREADMEY`，预期 `XYREADME` | 改路径、纠正关键词要重复定位；中文输入另需实测 |
| F02 | 清筛选后输入框与结果不一致 | 搜索 `XREADMEY` 时 0/6；Clear filters 后恢复 6 个文件，输入框仍显示 `XREADMEY`。History 清搜索后也保留旧文字却显示全部记录 | 用户无法判断筛选到底是否生效 |
| F03 | 搜到初始加载范围外的提交后，详情消失 | 专用 fixture 模拟搜索返回一个初始 snapshot 不含的旧提交；选中后 Commit details 元素不存在、文件按钮为 0 | 找到历史却不能继续审阅；原生超过第 80 条的 Git 链路仍需确认 |
| F04 | 短 History 裁掉提交信息 | 700×420，详情区高 190；元信息从 y=370 延伸至 y=550，外层底部 y=420 且 overflow:hidden | 作者、正文、hash 等信息无法完整呈现 |
| F05 | Stash 关闭后丢焦点 | Commit → More → Stashes → Close workflow，焦点落到 BODY | 键盘操作失去原位置，需要重新找入口 |

另有两个明确的设计风险：主文件列表看不出 staged / unstaged / staged+edits 的区别，主要依赖悬停；Staged 是文件筛选，提交仍包含选中文件的工作区修改。提交确认已解释范围并提示混合修改，但用户能否在确认前理解仍未验收。

版本也要先对齐：本轮看到的日常 VSCode 窗口加载 `keatonli.idea-git`，默认扩展目录中版本是 `0.3.0-beta.25`；`keatonli.kivo-git@0.5.1` 安装于独立测试配置。旧窗口的布局不作为 0.5.1 缺陷证据。

## 状态、优先级与通过标准

- **实测失败**：本轮 Webview 操作或界面测量已复现。
- **局部通过**：仅当前固定数据、尺寸、单项行为通过，不能代表完整流程。
- **待测**：已写验收步骤，还未在本轮执行；源码风险也属于待测。
- **P0**：提交、回滚等范围与数据保护的发布门槛。P0 用例不表示已发生数据丢失。
- **P1**：高频任务无法顺畅完成或关键信息读不到。
- **P2**：视觉一致性、发现入口、低频操作效率与细节。

每条用例分别记录三项结果：功能正确 / 操作连续 / 信息可读。不能用“元素存在”“没有横向溢出”替代后两项。

统一记录：实际版本、主题、系统缩放、VSCode zoom、视口、鼠标或触控板、文件规模、点击/按键数、返回后焦点、首个可见文件或 commit hash、失败截图。任务耗时首次建立基线，不预设未经测量的延迟成绩。

体验验收必须能够回答：用户不用反复悬停能否认出文件；确认前能否说出操作范围；刷新后是否仍在原位置；失败后是否知道下一步。真实鼠标/触控板的跟手程度由原设备测试记录，合成事件不替代体感。

## 现有测试能证明什么

现有 selection、resize、scroll、Graph、Git workflow 和消息隔离测试覆盖了不少正确性边界；现有 Webview 测试也检查了按钮、尺寸、部分焦点与桥接消息。这些覆盖保留。

本轮新增关注点是任务连续性、输入中间编辑、状态辨认、完整内容可达、用户对提交结果的预测，以及原生编辑器与 Webview 的回返。

特别注意：`scripts/test-webview.mjs` 的浅色、高对比、减少动画相关检查位于 `KIVO_CAPTURE_DIR` 条件分支，普通 Webview 测试不会执行这组检查；fixture 的主题是手动 CSS token。扩展 smoke 检查入口和激活，不能替代完整原生流程。本文没有把前一轮的 144 个测试结果作为本轮体验通过证据。

## 建议的优化顺序与 0.6 取舍

1. 先解决 F01/F02/F03/F04/F05，使搜索、详情阅读、取消回返可靠连续。
2. 再做日常链路验收：认文件 → 看 Diff → 勾选 → 理解范围 → 写 message → 审阅 → 提交后确认。重点明确文件状态、同名目录和提交范围，控制重复确认成本。
3. 再统一样式和手感：辅助字号、主题对比、焦点/hover/checked 区别、分隔条命中范围、窄短窗口预算、多个滚动区。
4. Push、Stash、Compare、冲突按“出去看 Diff / Merge，再回到原任务”的完整链路验收。

0.6 先以这些体验门槛为主。是否增加部分文件提交、Amend 等能力，应等提交范围理解和日常审阅流程验收后决定，避免把每个体验问题都变成新增功能。
